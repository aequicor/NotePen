# Трансляция документа планшет -> ПК

## Контекст

Трансляция нужна для режима, где NotePen на планшете управляет открытым документом, а NotePen на ПК пассивно отображает состояние. Штрихи, стирание и заметки уже синхронизируются через `SyncEngine`/`StrokeDelta`, поэтому viewport и выбранный инструмент вынесены в отдельный лёгкий кадр, не смешанный с LWW-дельтами аннотаций.

## Источник правды

- `sync/src/commonMain/kotlin/ru/kyamshanov/notepen/sync/domain/model/NetworkMessage.kt` — `NetworkMessage.ProjectionFrame`: `documentId`, `page`, `viewportOffsetX`, `viewportOffsetY`, `viewportScale`, `viewportCenterX`, `viewportCenterY`, `toolMode`.
- `sync/src/commonMain/kotlin/ru/kyamshanov/notepen/sync/domain/projection/DocumentBroadcastController.kt` — общий контроллер отправки/приёма кадров поверх `NetworkMessage`.
- `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/App.kt` — создаёт контроллер из `PeerServer.incomingMessages` и `SyncClient.incomingMessages`; при полном disconnect очищает последний принятый кадр.
- `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/BroadcastPresentation.kt` — единая common-логика UI-решений: валидный `documentId`, `activeBroadcastConnection(...)` по `PeerServer.connectedPeers` и `SyncClient.connectedHosts`, matching кадра к открытому документу, команда viewport и open/focus action.
- `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/RootContent.kt` + `app/byCompose/desktop/src/desktopMain/kotlin/main.kt` — ПК resolve'ит `documentId`: сначала через локальный `RemoteCatalogProvider.resolveUri(...)`, затем через `RemoteDocumentOpener.open(...)` для документов из каталога планшета; после этого вызывает `RootComponent.openDetailsExternally(uri)`, если editor screen ещё не активен.
- `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/DetailsContent.kt` + `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/tabs/TabSession.kt` — активный editor screen фокусирует уже открытую вкладку через `TabSession.focusDocument(...)` или открывает новую вкладку в focused panel; toolbar на ПК подсвечивает tool из последнего кадра, не меняя локальный `toolMode`.
- `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/EditorPanel.kt` — планшет-клиент публикует viewport/tool, ПК-сервер применяет кадры к документу с тем же `documentId` и показывает badge выбранного на планшете инструмента.
- `app/byCompose/common/src/commonMain/kotlin/ru/kyamshanov/notepen/DetailsContent.kt` + `app/byCompose/android/src/main/kotlin/ru/kyamshanov/replacementPlace/MainActivity.kt` — Android публикует открытые вкладки в `RemoteCatalog.openDocuments`, чтобы ПК мог открыть документ, которым управляет планшет; `content://` перед публикацией материализуется в cache-файл, потому что `WebSocketFileTransfer` читает обычные filesystem paths.
- `sync/src/commonMain/kotlin/ru/kyamshanov/notepen/sync/domain/DocumentTransferRequestHandler.kt` — обработчик `DocumentOpenRequest` работает и на `PeerServer`, и на `SyncClient`, поэтому клиентское устройство тоже может отдать файл подключённому хосту.
- `sync/src/commonMain/kotlin/ru/kyamshanov/notepen/sync/domain/RemoteDocumentOpener.kt` — opener тоже подключается к обоим портам. На desktop это критично: каталог планшета приходит через `PeerServer` (`RemoteCatalogHostCoordinator`), а не через desktop `SyncClient`.
- `sync/src/commonMain/kotlin/ru/kyamshanov/notepen/sync/domain/RemoteCatalogClientCoordinator.kt` — `RemoteCatalogHostCoordinator` на ПК переспрашивает каталог, когда Android-пир шлёт `RemoteCatalogChanged`; без этого ПК мог бы не узнать, что планшет только что открыл локальный документ.

## Инварианты

- Активный источник в текущем вертикальном срезе — клиентское устройство (`peerClient != null`, `peerServer == null`), то есть планшет. Серверный ПК (`peerServer != null`; на desktop `peerClient` тоже может быть не-null) только применяет кадры, чтобы не было борьбы двух viewport. Ролевые условия должны идти через `BroadcastPresentation.shouldPublishBroadcastFrame(...)` и `shouldApplyBroadcastFrame(...)`, а не через локальные `if` в Compose.
- Live-sync при подключённом пире включается автоматически, если пользователь явно не поставил документ на паузу. Этот контракт должен оставаться в `BroadcastPresentation.shouldAutoEnableLiveSync(...)`, иначе сценарий «подключил планшет и сразу работаешь» может снова зависеть от ручного тумблера.
- `ProjectionFrame` не заменяет `StrokeDelta`: новые штрихи, стирание и заметки должны продолжать идти через `SyncEngine`, иначе потеряется LWW-merge и offline queue.
- Кадры без `documentId` игнорируются новым контроллером; старые поля `page`, `viewportOffsetY`, `viewportScale` оставлены совместимыми с прежним projection-кодом.
- Единственная поддерживаемая runtime-ветка трансляции — `DocumentBroadcastController`. Старые `ProjectionHostController`/`ProjectionViewerController` и overlay, работавшие без `documentId`, удалены: они могли случайно отправить кадр, который новая документная трансляция обязана игнорировать. `ProjectionAttach`/`ProjectionDetach` пока остаются только как wire-совместимость со старыми сообщениями.
- `DocumentBroadcastController` отправляет первый frame сразу, а дальше держит pacing `PROJECTION_FRAME_INTERVAL_MS` и `conflate()`: при быстром scroll/zoom ПК должен получать свежий последний viewport, но WebSocket не должен получать кадр на каждую Compose snapshot-инвалидацию.
- `KtorSyncClient.connect(...)` обязан завершаться сразу после успешного secure pairing, пока WebSocket-сессия продолжает жить в фоне. Если ждать закрытия receive-loop, UI-подключение на планшете зависает, хотя сервер уже считает peer подключённым и может принимать `ProjectionFrame`.
- Pending pointer/viewport/tool внутри `DocumentBroadcastController` нельзя переносить между разными `documentId`. При переключении вкладки новый frame должен начинаться как состояние нового документа, иначе ПК может показать pointer/zoom/tool от предыдущей вкладки поверх уже другого PDF.
- `DocumentBroadcastController` нормализует `page`, viewport offsets/scale, `viewportCenterX`, `viewportCenterY` и pointer до публикации и при приёме. В wire-state нельзя выпускать `NaN`/`Infinity`: JSON-сериализация такого кадра может сорвать отправку, а ПК-viewer не должен зависеть от того, что каждый consumer отдельно чистит float.
- Ошибка отправки одного `ProjectionFrame` через transport не должна убивать job публикации в `DocumentBroadcastController`: следующий viewport/tool frame обязан уйти после transient failure. `CancellationException` при этом пробрасывается, чтобы lifecycle `close()` и parent-scope cancellation не маскировались.
- Полученный `ProjectionFrame` хранится как `StateFlow`, но должен жить не дольше активной связи: UI применяет его только пока `BroadcastPresentation.hasActiveBroadcastConnection(...)` видит хотя бы `connectedPeers` или `connectedHosts`, а `App` вызывает `DocumentBroadcastController.clearCurrentFrame()` при полном disconnect. Иначе старый кадр после reconnect мог бы заново открыть документ, подсветить старый инструмент или применить устаревший viewport.
- Remote tool в UI выбирается через `BroadcastPresentation.displayedToolMode(...)`: `ToolMode.NONE` из кадра — валидный remote state («рука») и должен переопределять локальный tool, а только `null` означает «remote tool неизвестен, показываем локальный». Публикуемый tool должен считаться через `projectedToolMode(...)`, чтобы аппаратный ластик/eraser override уходил в трансляцию как `ToolMode.ERASER`, даже если выбранный локальный инструмент остался `PEN`.
- Viewport-команда строится только через `BroadcastPresentation.broadcastViewportCommandForDocument(...)`: отрицательная page нормализуется к 0, NaN/Infinity в offset/scale/pan не должны доходить до `PdfViewerState`. Это защищает пассивный ПК-viewer от битого или старого сетевого кадра.
- Viewport для новых кадров переносится через центр: `viewportCenterX` — нормализованный X-центр видимого ряда PDF (`0..1`), `viewportCenterY` — page-relative Y-якорь (`pageIndex + normalizedYInsidePage`). Нельзя передавать Y-центр в локальных document-space px: `basePageWidthPx` зависит от ширины viewport на каждом устройстве, поэтому одинаковый pixel-Y на планшете и ПК попадает на разные страницы. ПК пересчитывает эти center-поля в локальные `targetPanX`/`targetPanY` через свой layout, viewport size и target scale. `viewportOffsetX`/`viewportOffsetY` остаются wire fallback для старых кадров.
- `BroadcastPresentation.broadcastViewportCommandForDocument(...)` должен различать нормализованный `viewportCenterX` и старый fallback `viewportOffsetX`. `viewportCenterX` — авторитетный X-якорь и может применяться вместе с вертикальным scroll, а после settled zoom обязан применяться вместе с `viewportCenterY`: после pinch у viewport есть оба смещения, X и Y. `viewportOffsetX` остаётся только fallback для старых кадров и применяется лишь когда предыдущий remote frame показывает реальное X-движение, иначе device-local px снова уведут ПК вбок.
- Чистое горизонтальное движение не должно вызывать `PdfViewerState.scrollToPage(...)`: на desktop этот вызов может временно центрировать X, а следующий `panGestureBy(...)` возвращает X к remote target, что выглядит как прыжки влево-вправо на каждом projection frame. Если в кадре есть `viewportCenterY`, zoom тоже не должен идти через `scrollToPage(...)`: иначе разные высоты экранов дают разный центр видимой области после масштабирования. `BroadcastViewportCommand.shouldScroll` нужен только для fallback-кадров без `viewportCenterY`.
- `EditorPanel` сначала применяет remote zoom, затем либо fallback `scrollToPage(...)`, либо delta к `targetPanX`/`targetPanY` от свежего `pdfViewerState.pan`; иначе `setScalePercent(...)` может поменять pan и desktop окажется не на том смещении, которое следует из viewport center. Кадры со `scaleChange` на принимающей стороне не применяются сразу: `collectLatest` ждёт короткое zoom idle window, отменяет промежуточные кадры новым frame и применяет только последний scale вместе с X/Y-якорями. Это убирает вертикальные скачки и мигание PDF на ПК во время pinch, но сохраняет финальный viewport после остановки зума.
- Программный pan из broadcast-команды в `EditorPanel` должен оборачивать `PdfViewerState.panGestureBy(...)` в `beginPanGesture()`/`endPanGesture()`. На desktop `panGestureBy(...)` опирается на внутренний `dragRawPan`; если не сбросить его перед post-zoom коррекцией, финальный Y-якорь может примениться от старой drag-базы, и ПК останется на другой странице до первого ручного scroll.
- Публикуемый `ProjectionFrame` должен строиться из одного effective-снимка viewer'а: `effectivePan` + `effectiveZoom` используются не только для `viewportCenterX/Y`, но и для `page`/`pageOffsetPx`. Нельзя смешивать effective center с committed `firstVisiblePageIndex`/`firstVisiblePageOffsetPx`: во время Android pinch/desktop wheel-burst визуально уже показана новая область, а committed `pan/zoom` обновляются позже, из-за чего ПК может остаться на старой странице после zoom.
- `RootComponent.openDetailsExternally(uri)` должен быть idempotent: если документ уже есть в back stack, он фокусируется через `popTo`, а не открывается дублем. Это важно, потому что broadcast frame может приходить часто.
- Если `DetailsContent` уже открыт, broadcast не должен плодить Decompose screens: документ ищется среди вкладок по canonical sync id, а отсутствующий документ открывается вкладкой в текущей focused panel.
- `RemoteCatalog.openDocuments` должен публиковать только локально открытые документы. Remote-кешированные файлы фильтруются в `DetailsContent`, чтобы устройство не переобъявляло чужой документ как свой источник transfer.
- `RemoteCatalog.openDocuments[].documentId` берётся из уже созданного `PdfDocumentState.documentId`, а не заново из `syncDocumentIdFor(path)`. Это держит catalog, `ProjectionFrame` и `SyncEngine` на одном wire id даже в гонке, где content-addressed identity cache прогрелся после создания вкладки.
- На Android `OpenDocumentInfo.absolutePath` для `content://` нельзя отдавать напрямую в `RemoteCatalogProvider`: перед `openDocumentsRegistry.publish(...)` `MainActivity` копирует такой URI в `cacheDir/sync/open-documents/<safe-name>`. Иначе `DocumentTransferRequestHandler` дошёл бы до `WebSocketFileTransfer`, а тот упал бы на `File("content://...").readBytes()`. Публикация open-documents на Android latest-wins: новая порция отменяет предыдущую materialize-задачу, и перед финальным `publish(...)` проверяется cancellation, чтобы медленное копирование не переопубликовало закрытый документ.
- Изменение `RemoteCatalog.openDocuments` должно доходить до desktop host через `RemoteCatalogChanged` и host-side re-request. `RemoteCatalogProvider.broadcastChanges(...)` рассылает сигнал при изменении локального `OpenDocumentsProvider`, а `RemoteCatalogHostCoordinator` обязан кешировать `openDocuments` из ответа, потому что `RootContent`/`RemoteDocumentOpener` ищут планшетный документ именно в `remoteCatalogCache.catalogs`.
- `DocumentTransferRequestHandler` должен не только отвечать `DocumentNotFound`, но и успешно стримить `openDocuments`-файл тому host/peer, которому ранее был собран catalog snapshot. Чанки обязаны нести тот же `documentId`, чтобы `RemoteDocumentOpener` отфильтровал параллельные transfer'ы.
- Desktop broadcast resolver не должен ограничиваться локальным provider: планшет-локальный файл появляется только в remote catalog и должен открываться через `RemoteDocumentOpener`, который скачивает кеш-копию и регистрирует `localPath -> documentId`.
- Если `RemoteDocumentOpener` работает в desktop session, он обязан иметь и `client`, и `server`: документ от подключённого Android-пира запрашивается через `PeerServer.send(...)`, а документ от другого host — через `SyncClient.send(...)`.
- Когда у `RemoteDocumentOpener` есть оба transport, `DocumentOpenRequest` выбирает канал по `connectedHosts`/`connectedPeers`, а не слепо отправляется сначала в `SyncClient`. Иначе desktop может не запросить файл у Android-пира, который подключён именно как peer к `PeerServer`.
- UI-решения, зависящие от наличия связи (`App.clearCurrentFrame`, auto-open в `RootContent`, auto-live-sync и broadcast badge/viewport в editor), должны использовать общий `activeBroadcastConnection(...)`. Локальные `if (peerServer != null) connectedPeers else connectedHosts` ломают desktop runtime с двумя транспортами.
- Desktop должен открывать документ планшета не только по первому `ProjectionFrame`, но и по `RemoteCatalog.openDocuments`: пользовательский сценарий начинается с «открыл файл на планшете», а viewport/tool frame может прийти позже или вообще не прийти до первого жеста. `main.kt` передаёт в `App` поток первого remote-open `documentId`, а `RootContent` использует тот же `broadcastDocumentUriFor` resolver, чтобы скачать/открыть файл через `RemoteDocumentOpener` и не дублировать transfer-логику.
- `RemoteDocumentOpener.open(...)` ждёт появления `documentId` в `RemoteCatalog.recent/openDocuments` в пределах `requestTimeoutMs`. Это закрывает race, где `ProjectionFrame` от планшета пришёл на ПК раньше, чем `RemoteCatalogChanged` успел подтянуть список открытых документов.
- `RemoteDocumentOpener.open(...)` должен подписаться на `DocumentNotFound` и `FileTransferStart/FileChunk` до отправки `DocumentOpenRequest`. На реальном Ktor-канале маленький PDF может быть отстримлен сразу после request, и подписка после send теряет первые transfer-сообщения в `SharedFlow` без replay.
- После `DocumentOpenRequest` `RemoteDocumentOpener` обязан собрать входящие `FileTransferStart`/`FileChunk` только для запрошенного `documentId`, записать кеш-копию и зарегистрировать `localPath -> documentId`. Иначе скачанный планшетный файл откроется как новый локальный документ и `ProjectionFrame`/`StrokeDelta` разойдутся по разным ids.
- `RemoteDocumentOpener.open(documentId)` должен переиспользовать уже скачанный файл даже без явного `displayName`: имя берётся из `RemoteCatalog.recent/openDocuments`. Это важно для auto-open по `ProjectionFrame`, где UI знает только `documentId`, а повторные кадры не должны заново стримить тот же планшетный PDF.
